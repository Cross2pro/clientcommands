# crackPlayerRNG Command Implementation Analysis

## Overview
The `crackPlayerRNG` command (implemented as `/ccrackrng` in the code) is a sophisticated feature that cracks the player's random number generator (RNG) seed in Minecraft. This allows players to predict and manipulate random events that use the player's RNG instance.

## Purpose
The player RNG in Minecraft controls various random events including:
- Item throwing trajectories
- Item durability loss (Unbreaking enchantment calculations)
- Enchanting outcomes
- Food consumption particles
- Crossbow usage
- Anvil usage
- Equipment sounds
- And many other player-related random events

By cracking this seed, players can:
1. **Predict outcomes** - Know in advance what random events will occur
2. **Manipulate outcomes** - Throw items to advance the RNG to a desired state
3. **Optimize gameplay** - For example, avoid tool breaking by advancing RNG past bad rolls

## Implementation Architecture

### 1. Command Entry Point
**File**: `CrackRNGCommand.java`

```java
public static void register(CommandDispatcher<FabricClientCommandSource> dispatcher) {
    dispatcher.register(literal("ccrackrng")
        .executes(ctx -> crackPlayerRNG(ctx.getSource())));
}

private static int crackPlayerRNG(FabricClientCommandSource source) throws CommandSyntaxException {
    ServerBrandManager.rngWarning();  // Warn if server is modded
    CCrackRng.crack(seed -> {
        source.sendFeedback(Component.translatable("commands.ccrackrng.success", 
            Long.toHexString(seed)));
        PlayerRandCracker.setSeed(seed);
        Configs.playerCrackState = PlayerRandCracker.CrackState.CRACKED;
    });
    return Command.SINGLE_SUCCESS;
}
```

### 2. Core Cracking Logic
**File**: `CCrackRng.java`

The cracking process works by:

#### Step 1: Item Throwing
- Forces player to look straight up (pitch = 90°)
- Throws 10 items in succession
- Each item throw consumes 4 RNG calls
- Captures the velocity vector of each thrown item

```java
public static final int NUM_THROWS = 10;
public static final float MAX_ERROR = 0.00883889f;  // Computed by brute force
```

#### Step 2: Data Collection
When items spawn, their motion vectors are captured:

```java
public static void onEntityCreation(ClientboundAddEntityPacket packet) {
    if (Configs.playerCrackState == PlayerRandCracker.CrackState.CRACKING) {
        if (CCrackRng.expectedItems > 0) {
            // Calculate horizontal speed from velocity components
            float nextFloat = (float) Math.sqrt(
                packet.getMovement().x * packet.getMovement().x + 
                packet.getMovement().z * packet.getMovement().z
            ) * 50f;
            CCrackRng.nextFloats[NUM_THROWS - CCrackRng.expectedItems] = nextFloat;
            CCrackRng.expectedItems--;
        }
    }
}
```

The horizontal speed is proportional to the random float value generated for item throwing.

#### Step 3: Seed Recovery
**File**: `CCrackRngGen.java` (Generated by LattiCG library)

Uses lattice-based cryptanalysis to recover the seed:
- Takes 10 float ranges (min/max with error tolerance)
- Uses the LattiCG library (lattice-based RNG cracking)
- Searches through seed space efficiently using mathematical lattices
- Returns matching seed(s)

```java
public static LongStream getSeeds(
    float minNextFloat1, float maxNextFloat1, 
    float minNextFloat2, float maxNextFloat2,
    // ... 10 pairs of min/max values
) {
    // Uses BASIS, ORIGIN, ROOT_INV, ROOT_ORIGIN matrices
    // These are precomputed lattice bases for efficient search
    return EnumerateRt.enumerate(BASIS, ORIGIN, builder.build(), 
                                  ROOT_INV, ROOT_ORIGIN)
        .mapToLong(vec -> (vec.get(0).getNumerator().longValue() * 
                          0x641598c21879L + 0x60dd589d4b7eL) & MASK);
}
```

#### Step 4: Retry Logic
If cracking fails (multiple or zero seeds found):
- Retries up to 5 times
- Each retry throws 10 more items
- Error tolerance accounts for network latency and floating-point precision

### 3. RNG Maintenance System
**File**: `PlayerRandCracker.java`

Once cracked, the mod maintains synchronization with the server's RNG state:

#### RNG Implementation
Mirrors Java's Linear Congruential Generator (LCG):

```java
private static final long MULTIPLIER = 0x5deece66dL;
private static final long ADDEND = 0xbL;
private static final long MASK = (1L << 48) - 1;

private static int next(int bits) {
    seed = (seed * MULTIPLIER + ADDEND) & MASK;
    return (int) (seed >>> (48 - bits));
}
```

#### Event Detection System
Uses Mixin injections to detect RNG calls:

```java
public static void onDropItem() {
    if (canMaintainPlayerRNG(RNGCallType.DROP_ITEM)) {
        for (int i = 0; i < 4; i++) {
            nextInt();  // Advance local RNG by 4 calls
        }
    } else {
        resetCracker(RNGCallType.DROP_ITEM, false);
    }
}
```

Tracked events include:
- `DROP_ITEM` - 4 RNG calls per item throw
- `FOOD` / `DRINK` - 3 calls per sound + particles
- `UNBREAKING` - Variable calls based on damage
- `CROSSBOW` - 1-2 calls depending on version
- `ANVIL` - 1 call
- `ENCHANTING` - 1 call
- And 20+ other event types

#### Reset Detection
If an unexpected RNG call occurs, the system resets:

```java
private static void resetCracker(RNGCallType reason) {
    if (Configs.playerCrackState != CrackState.UNCRACKED) {
        ClientCommandHelper.sendError(
            Component.translatable("playerManip.reset", reason.resetMessage));
        Configs.playerCrackState = CrackState.UNCRACKED;
    }
}
```

### 4. RNG Manipulation Features

#### Item Throwing Utility
Can advance RNG to desired state:

```java
public static ThrowItemsResult throwItemsUntil(
    Predicate<Random> condition, int max
) {
    long seed = PlayerRandCracker.seed;
    Random rand = new Random(seed ^ MULTIPLIER);
    
    // Simulate forward to find how many items needed
    int itemsNeeded = 0;
    for (; itemsNeeded <= max && !condition.test(rand); itemsNeeded++) {
        for (int i = 0; i < 4; i++) {
            seed = (seed * MULTIPLIER + ADDEND) & MASK;
        }
        rand.setSeed(seed ^ MULTIPLIER);
    }
    
    // Actually throw the items
    for (int i = 0; i < itemsNeeded; i++) {
        throwItem();
    }
    
    return new ThrowItemsResult(Type.SUCCESS);
}
```

#### Infinite Tools Feature
When tools would break, automatically advances RNG:

```java
if (Configs.infiniteTools && Configs.playerCrackState.knowsSeed()) {
    ThrowItemsResult result = throwItemsUntil(rand -> {
        for (int i = 0; i < amount; i++) {
            if (isArmor && rand.nextFloat() < 0.6) {
                return false;  // Would take damage
            }
            if (rand.nextInt(unbreakingLevel + 1) == 0) {
                return false;  // Unbreaking failed
            }
        }
        return true;  // All damage avoided

}
```

### 6. Task Management
**File**: `ItemThrowTask.java`

Manages asynchronous item throwing:

```java
public abstract class ItemThrowTask extends SimpleTask {
    @Override
    protected void onTick() {
        itemThrowsAllowedThisTick += Configs.itemThrowsPerTick;
        
        while (itemThrowsAllowedThisTick >= 1 && sentItemThrows < totalItemsToThrow) {
            itemThrowsAllowedThisTick--;
            PlayerRandCracker.ThrowItemsResult result = PlayerRandCracker.throwItem();
            if (!result.isSuccess()) {
                onFailedToThrowItem(result);
                return;
            }
            onItemThrown(++sentItemThrows, totalItemsToThrow);
        }
    }
}
```

Handles:
- Rate limiting (configurable throws per tick)
- Creative vs Survival mode
- Item availability checking
- Network synchronization
- Failure recovery

4. **Translation System** - Localized messages

## Technical Challenges

### 1. Network Latency
- Items may spawn out of order
- Velocity values may have precision loss
- Solution: Error tolerance (MAX_ERROR = 0.00883889f) and retries

### 2. Maintaining Synchronization
- Server's RNG must match client's prediction
- Any missed event causes desync
- Solution: Extensive Mixin coverage + reset on unexpected calls

### 3. Version Compatibility
- Different MC versions have different RNG call patterns
- Solution: `MultiVersionCompat` for version-specific logic

### 4. Modded Servers
- Paper and other servers may not maintain player RNG properly
- Solution: Server brand detection and warnings

## Configuration

Users can configure:
- `playerCrackState` - Current state (UNCRACKED/CRACKING/CRACKED)
- `playerRNGMaintenance` - Auto-maintain RNG state
- `infiniteTools` - Prevent tool breaking
- `toolBreakWarning` - Warning when tool near breaking
- `itemThrowsPerTick` - Speed of item throwing
- `chorusManipulation` - Special handling for chorus fruit

## Limitations

1. **Server Requirements**
   - Only works on vanilla-like servers
   - Paper and some plugins break player RNG determinism

2. **Resource Requirements**
   - Needs items to throw (64+ recommended)
   - Requires player to look up for ~5 seconds

3. **Network Requirements**
   - Higher latency increases failure rate
   - May need multiple attempts on poor connections

4. **Scope**
   - Only cracks player RNG (not world RNG or other entity RNG)
   - Some events still cause resets (XP orbs in 1.17+)

## Success Rate
- First attempt: ~80% success rate
- After retries (max 5): >95% success rate
- Failure usually means server doesn't maintain deterministic player RNG

## Security Considerations
This is a client-side feature that:
- Does NOT give server-side advantages in PvP
- Does NOT break server security
- Does NOT allow cheating beyond client prediction
- Server still validates all actions

It's essentially a sophisticated prediction tool, similar to using external calculators but built into the client.
